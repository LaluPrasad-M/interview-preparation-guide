# Webhook Signatures

> [!tldr]
> HMAC over the raw body, compared in constant time, with a timestamp to kill replays. Three details, three production outages if you miss them.

---

## The mechanism

Webhooks are just HTTP POST requests to a public URL, so you need a way to prove the request actually came from the sender and that the payload was not tampered with in transit.

The whole process relies on a shared secret, a cryptographic key generated by the sender and securely shared with the receiver, usually stored in environment variables.

1. **Sender.** The sender takes the payload, mixes it with the shared secret using an algorithm, usually SHA-256, and creates a signature.
2. **Transport.** The sender attaches the signature to the HTTP request.
3. **Receiver.** The receiver takes the incoming payload and mixes it with its own copy of the shared secret using the exact same algorithm.
4. **Validation.** If the receiver's generated signature exactly matches the attached one, the webhook is authentic.

---

## How it is carried

Signatures are almost exclusively carried in HTTP headers.

```http
POST /api/webhooks/receive HTTP/1.1
Host: your-domain.com
Content-Type: application/json
X-Webhook-Signature: a3b4c5d6e7f8a9b0...
```

Industry leaders often include a timestamp in the header to prevent replay attacks, formatted like `Stripe-Signature: t=1492774577,v1=5257a869e7...`.

## Signing, on the sender side

```js
const crypto = require('crypto');

function signWebhook(payloadObject, sharedSecret) {
  // 1. Convert the payload to a string exactly as it will be sent
  const stringifiedPayload = JSON.stringify(payloadObject);

  // 2. Generate the HMAC-SHA256 signature
  const signature = crypto
    .createHmac('sha256', sharedSecret)
    .update(stringifiedPayload)
    .digest('hex');

  return signature;
}

const secret = 'whsec_super_secret_key_123';
const data = { event: 'user.created', userId: 99 };

const mySignature = signWebhook(data, secret);
// Attach mySignature to the X-Webhook-Signature header
```

## Validating, on the receiver side

If a malicious actor intercepted the request and changed `userId` from 99 to 100, the hash you generate will be entirely different from the one in the header, and validation fails.

```js
const crypto = require('crypto');

function validateWebhook(rawBody, incomingSignature, sharedSecret) {
  // 1. Recreate the signature using the exact raw body received
  const expectedSignature = crypto
    .createHmac('sha256', sharedSecret)
    .update(rawBody)
    .digest('hex');

  // 2. Compare the signatures securely
  try {
    // Convert to buffers for constant time comparison
    const expectedBuffer = Buffer.from(expectedSignature, 'hex');
    const incomingBuffer = Buffer.from(incomingSignature, 'hex');

    // timingSafeEqual prevents timing attacks
    if (expectedBuffer.length !== incomingBuffer.length) {
      return false;
    }

    return crypto.timingSafeEqual(expectedBuffer, incomingBuffer);
  } catch (error) {
    return false;
  }
}
```

## The three production pitfalls

### 1. The raw body trap

This is the number one reason webhook validation fails for developers.

You cannot use the parsed JSON object, for example `req.body` in Express. You must hash the exact raw byte stream of the HTTP request body.

If your framework parses the JSON and you then `JSON.stringify()` it back, the spacing, ordering or character encoding might change slightly, which completely alters the resulting hash.

### 2. Timing attacks

Do not use standard string comparison, `===`. Standard equality returns false the moment it finds a mismatched character, and an attacker can measure microscopic differences in response times to guess the signature character by character.

Always use a constant time comparison function like `crypto.timingSafeEqual`.

### 3. Replay attacks

A valid signature proves the payload was not tampered with, but it does not prevent an attacker intercepting a legitimate webhook, for example a refund, and sending that same valid request 100 times.

**The fix.** The sender includes a timestamp in the signed payload or header. The receiver checks it and rejects any webhook older than a few minutes, for example 5, which effectively kills replay attacks.
